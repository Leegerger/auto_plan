# External acceptance runner

The external runner uses Chromium against a selected HTTPS application. It never starts a replacement server, stores passwords/session cookies, or calls a private write endpoint. The separate `adapter_server.py` provides an explicitly synthetic local preparation target for checking the scripts.

Copy `external.example.json` to a non-secret run configuration and fill its environment fields. For an authorized disposable Oracle run, set `target.kind` to `PLAN_TEST` and record the exact `AP_TEST_` namespace, origin, retained prefix, image digest, source commit, migrations, runtime/native/browser versions, hardware, network/proxy path, actual cgroup CPU/memory allocation, workers/threads, pool maximum/observed use and peak resources. A target declaration records the operator's attestation; it does not independently prove where the server connects.

The runner requires the complete frozen source inputs, plan, execution context, baseline, scope and exact production clock. It rejects changed hashes or bindings. Use the existing injected clock at the test-infrastructure boundary. No production configuration switch or clock bypass is provided. Record any namespace/clock wrapper separately from actual product entrypoint observations.

For an empty disposable target, `prepare_external.py` validates the public first import, applies it with an operation UUID, then previews and explicitly adopts the frozen source plan. This synthetic test adoption establishes the baseline. It writes each UUID before submission and verifies the original UUID after a transport failure. It requires one authorized account through private stdin and writes a non-secret `run-config.json` with the actual tokens. It refuses existing plans, rolling history and protected companions that need additional public context actions. Adoption also requires an executable exact-source preview. Directly importing an already changed local demand can fail that requirement before any timed observation; r20-near-decrease reproduced 13 pending cross-week confirmations. Local cases need authentic prior original-demand adoption, then a public whole-file demand replacement and complete source-order verification. This preparation is unfinished. The script never resets or drops a schema.

```bash
# Supply {"accounts":[{"username":"...","password":"..."}]} through a private stdin channel.
PYTHONPATH=src:. python scripts/acceptance/prepare_external.py --config /tmp/run.json --output /tmp/prepared-new
# Supply a fresh in-memory login payload again. No credential file is required.
PLAYWRIGHT_BROWSERS_PATH=/tmp/auto-plan-playwright PYTHONPATH=src:. node frontend/tests/acceptance/run.mjs --config /tmp/prepared-new/run-config.json --output /tmp/observed-solo-new --mode solo --operations selection,week,day,single_cell,batch_preview,shared_save
```

The general five-context path accepts exactly five distinct authorized test accounts through stdin with `--mode five_automated_editors_one_computation`; one owns the computation. Four others preview 99 pieces, preview 100, undo both complete actions and save their original complete line/date blocks. That original-block save can leave persisted business state unchanged, so this path has no qualified full load-matrix result. The later [private shared-save probe](private-local-drafts.md) has a separate recorded representative pass for five browser contexts editing private drafts while one native job runs. Its server uses an in-memory test adapter; the separate packaged Oracle runs establish their own persistence and lifecycle evidence.

A future full shared-edit load schedule must predeclare complete background states and preserve the primary action's exact frozen source at the server's accepted pin. Each background editor must produce actual changed immutable state under that operation's public contract. Retain complete requests, accepted outcomes, exact before/after contents, actor attribution and overlapping activity intervals for all five repeats. Plan/demand commands retain their original UUID verification. Maintained-input edits use their own optimistic-version contract. The approved A2 implementation closeout covers eight `r20-loose` solo operations, each five times including the first: selection, week, day, single-cell preview, batch preview, shared save, import validation and all-replan. It also records the separate five-browser shared-save probe. Local/new-week end-to-end timings, the `local-v2` and `rolling-v2` families, extended distributions and full five-repeat load matrices remain `not_run`. This scope does not claim final company-account, human, reference-plan or site acceptance. The [runtime report](../validation/acceptance/runtime.md) lists the evidence and its boundaries.

Every selected operation runs five times, including the first. Gates are 3 seconds for selection and week/day views, 15 for single-cell and batch preview, 30 for import validation and shared save (60 under five-editor concurrent load), 60 for a local candidate and 180 for new-week/all-replan candidates. The browser captures the actual click or change event. Completion requires the useful result to appear and finish rendering. The existing Node-observed duration remains the gate duration. A separate browser timestamp after the checked result and two animation frames is diagnostic evidence; it does not replace older observations. A progress message never ends candidate timing. Candidate timing includes submission, queue/network, polling, content request and displayed output tables. A further public evaluation verifies the full frozen snapshot/request binding, executable/protection state and all 33 objective coordinates, with that verification span reported separately.

Selection requires the selected summary and quantity form to match the named row, then requires the zero-selection summary and disabled quantity action after deselection. Week navigation first displays week 1 and verifies week 15 is absent, then measures the distinct move to week 15. Day navigation similarly requires distinct populated source and target days. A manual preview must submit exactly the named action and scope. Single-cell output is exactly 419,999 with one final-week M00 gap; the two named batch clears produce exactly 419,800 with gaps of 100 for M00 and M02. Every other dated weekly result and protected source row must remain unchanged.

Shared-save timing uses a real final-date M00 reduction from 100 to 99. After the committed message and useful modified row render, verification binds the original UUID to a new immutable revision and reads the complete persisted source again through a browser fetch with caching disabled. The runner explicitly restores the original complete source outside timing before the next repeat. Saving an unchanged 100-piece row cannot satisfy this operation. Cleanup failures invalidate an earlier pass and leave later dependent repeats `not_run`.

Each repeat records the fresh source tokens used for setup. Successful saves and their explicit restorations advance the revision, while the frozen source, input version and adoption stay fixed. For a separate invocation against that restored target, refresh `bindings.source_revision` from a fresh public read outside timing, and retain the preceding report. Initial preflight still checks all configured tokens and the complete source. Page setup waits allow 180 seconds outside the measured interval; each repeat records setup duration separately. This does not change any measured gate.

Use `--operations local` with a frozen near/far local scenario. The fixed batch action clears M00 and M02 on the final date of a loose source, with independently expected output 419,800 and gap 200. Single-cell edits should use the final-date M00 segment. Both previews remain local.

Use `--operations new_week` only with a prepared rolling scenario, and `--operations all_replan` with its matching broad-scope scenario. Use `--operations import_validation` alone in solo mode on a fresh empty target with `workbook` in the configuration. Download that target's public `/api/initialization/template.xlsx`, then populate it without guessing its columns:

```bash
PYTHONPATH=src:. python scripts/acceptance/workbook.py --scenario r20-loose --template /tmp/standard.xlsx --output /tmp/frozen-source.xlsx
```

The builder also writes `/tmp/frozen-source.xlsx.acceptance.json`. Keep that non-secret provenance beside the workbook, or configure `workbook_provenance` explicitly. Before timing, the runner checks the workbook byte hash, scenario, frozen import hash and manifest hash. After upload it compares the complete returned payload, all prepared masters/parameters/calendar/demands/coverage/reset/execution/initial states and all 4,200 named segments with the frozen import, then checks the independent output. It also checks that input contents and all shared/adoption tokens stayed unchanged. A smaller valid workbook cannot satisfy this observation.

Large import responses require the browser's complete already-consumed response to remain available for evidence capture. After page initialization and before the input clock, the runner enables durable CDP Network messages with explicit buffer limits; each repeat records those settings. Ordinary response parsing, complete business assertions and useful rendered completion remain required. Earlier uploads that started but then lost inspector response capture retain null completion durations and no timing verdict. A later complete rerun supplies its own verdict.

These slots remain `not_run` until their actual browser/activity schedule is qualified. This resolves the interpretation; remaining implementation and qualification are internal work.

The report retains every repeat, first-repeat marker, click/feedback/full-render times, gate result, request spans, exact vectors, candidate/stage bounds, commit/job/candidate IDs, screenshots, hashes and environment data. Runner, assertion/navigation helpers and frozen source hashes are separate. Setup failures have null measured durations. Any later assertion, screenshot or cleanup failure changes a previous pass to fail. The runner verifies every original job submission UUID, including lost acknowledgments, and stops/polls each resulting job to a terminal state. Queued and running are not terminal states. Every repeat requires an empty local queue and no active jobs after cleanup.

Missing reproducible environment fields are listed as `not_run`. The runner exits unsuccessfully on a failed automated gate. Reference confirmation, real accounts/company authentication, twenty-account permissions and five-human business acceptance remain `not_run` regardless of synthetic results. Run the five-editor command separately from solo; both reports are required.

An optional `AUTO_PLAN_BROWSER_EXTERNAL_URL` disables the fixture web server in the existing Playwright configuration. Existing fixture tests still have their own fixture requirements. The standalone acceptance runner above supplies the complete external flow.

```bash

```
