# Durable calculation jobs

Automatic scheduling uses the Oracle queue. POST `/jobs` accepts a client `submission_id`, the shared revision/input/adoption tokens and a `SolveRequest`. The server generates a separate job UUID and freezes only the saved shared state. An accepted calculation does not create a shared revision or adoption. Browser drafts must first be saved before their changes can participate.

An unknown submission acknowledgement keeps its original UUID. POST `/jobs/verify` returns the exact `ACCEPTED` acknowledgement or a permanent `ABORTED_VOID`. The browser must receive one of those outcomes before starting another submission. A void UUID can never admit a late request.

Each account may have one running job and one queued job. The queue follows committed FIFO order, including waiting behind an account that already has a running job. `AUTO_PLAN_JOB_QUEUE_CAPACITY` defaults to 20. Worker count defaults to allocated CPU cores minus one, using affinity and available cgroup limits. An allocation below two cores has no default worker and rejects computation as unavailable. `AUTO_PLAN_JOB_WORKERS` can reduce that count. Each active worker runs one native thread. All Oracle operations use the existing application pool, initially configured for at most ten connections; compute/native processes receive no Oracle connections or credentials.

GET `/jobs` and `/jobs/{id}` report execution state independently of result validity and proof. Completion does not prove infeasibility or global optimality. A stopped, failed or interrupted job may retain a complete candidate. Status polling does not extend candidate retention. Only a successful authorized candidate content view extends its thirty-day retention point. Expired references return 410. Shared revisions and adoptions retain applied content independently.

Submitters and administrators can stop a known job. Administrator-only accounts cannot list or view business jobs/candidates. Closing the browser, logging out or an expired session does not cancel work. Revoking editor authorization cancels queued work and requests cooperative stopping for running work. After ten seconds without a response the controller kills and reaps the owned process group and records interruption. It preserves only complete durable candidates.

Candidate application carries `apply_candidate` references and optional selected identities. The server pins original source revision and input version. It cannot be rebased by changing browser command tokens. Shared PlanService performs current authorization, input/effect/protection checks and complete evaluation. Partial selection creates a fresh certificate and draft proposal. Only explicit adoption advances the adopted baseline. POST `/jobs/{id}/rerun` accepts a new submission UUID and reuses the exact original frozen input, including its original time and baseline.

## Lifecycle integration

`job_api.configure_jobs(app)` constructs `OracleJobStore` and `JobController` using the existing access pool and wires the same-cursor authorization-revocation hook. It does not start dispatch. The deployment lifecycle must verify migrations through 005, call access startup to invalidate sessions, check plan integrity, call controller recovery/integrity, and only then start dispatch and open readiness. `JobController.recover_startup()` checks job/key/frozen/candidate integrity, creates a controller generation and interrupts prior running jobs. Queued jobs retain FIFO order. `check_consistency()` is read-only.

At SIGTERM the entrypoint must call `controller.close_admission()` before draining requests. Then `shutdown(timeout=30)` signals all owned workers together, records cooperative stop intent independently of stop timers, broadcasts forced process-group kills and reaps against one total deadline. The pool closes afterward. An explicitly supplied controller is also wired through the app lifespan for startup/shutdown. The deployment readiness and actual container signal entrypoint are owned by the deployment ticket.

Fresh outer compute processes run `auto_plan.job_compute`. They use length-prefixed bounded messages and a two-message queue with backpressure. Candidate/frozen payloads have a 64 MiB limit; metadata frames have a 64 KiB limit. Malformed, truncated or oversized messages fail the run without replacing a prior complete candidate. Native solver routes still use separate fresh exec processes. Stderr tails, native output and numerical-library threads are bounded.
